1. 一句话定义

XM（eXtended Module，扩展模块）是 FastTracker II 的原生模块文件格式，1994 年由 Triton 的两位作者 Fredrik "Mr.H" Huss 与 Magnus "Vogue" Högdahl 设计。它是 4 声道 ProTracker MOD 格式的全面扩展：声道数上限提升到 32，引入"乐器（instrument）"层级，增加音量/声像包络与自动颤音，并在采样层支持 8/16 位与循环点。

从文件结构上看，XM 不是音频编码，而是一份曲谱 + 采样库的归档：它描述"在什么时间、用什么音高、什么音量、在哪个声道上播放哪段采样，以及施加什么效果"，实际发声由播放器（replayer）实时合成。

本仓库 ft2-clone 即是一个以"逐比特精确复刻"为目标的 FastTracker II 克隆，其 XM 加载器 src/modloaders/ft2_load_xm.c 与保存器 ft2_module_saver.c 直接移植自原版 FT2 源码。

2. 在 tracker 模块格式家族中的位置

格式全称诞生魔数 / 标识最大声道乐器层级频率表模式
MODAmiga Module1987偏移 1080 处 M.K. 等4无（扁平采样）Amiga
S3MScream Tracker 3 Module1990偏移 0x2C 处 SCRM32无可选
XMeXtended Module1994偏移 0 处 "Extended Module: "32有线性 / Amiga 可选
ITImpulse Tracker Module1996偏移 0 处 IMPM64有可选 + 滤波/NNA

XM 的历史意义在于：它是第一个把"采样 + 包络 + 乐器抽象"完整写进公开文档的模块格式，也因此成了 1990 年代中后期 PC 端作曲的事实标准之一，其规范被 OpenMPT、libxm、libmodplug 等大量第三方实现遵循。

本仓库的格式判定顺序见 src/ft2_module_loader.c：先探测 BEM、DIGI Booster、IT，再在偏移 0 处比对 17 字节字符串 "Extended Module: "，命中即判为 FORMAT_XM（ft2_module_loader.c:145-150）。

3. 整体文件布局

XM 文件是三段式串行结构，没有全局索引表，因此必须顺序解析：

┌──────────────────────────────────────────────┐
│ 1. 主头部 (XM Header)          336 字节       │
│    - 魔数、歌曲名、版本、默认速度/BPM          │
│    - 256 字节 order 表（播放顺序）             │
├──────────────────────────────────────────────┤
│ 2. 模式数据 (Pattern Data)      N × 变长       │
│    - 每个 pattern 自带头部 + 打包(packed)数据    │
├──────────────────────────────────────────────┤
│ 3. 乐器数据 (Instruments)       M × 变长       │
│    - 乐器头部 263 字节 + 采样头部 40 字节/个     │
│    - 随后紧跟所有采样的 delta 编码波形数据        │
└──────────────────────────────────────────────┘

关键的顺序陷阱：三段在文件中的先后顺序随版本而变，加载器必须分支处理（ft2_load_xm.c:106-140）：

  • v1.02 / v1.03：头部 → 全部乐器头部 → 全部 pattern → 全部采样数据
  • v1.04（最终版）：头部 → 全部 pattern → 逐乐器（头部 + 采样数据）

这是 XM 最著名的实现坑之一。本仓库显式实现了两条解析路径，这也是为什么 loadPatterns() 与 loadInstrHeader()/loadInstrSample() 被拆成可独立调用的两个阶段。

4. 主头部（336 字节）

对应代码结构体 xmHdr_t（src/ft2_replayer.h:98-110，按 1 字节对齐打包 #pragma pack(1)）：

偏移长度字段（代码名）含义
0x0017ID魔数，固定 ASCII "Extended Module: "（含末尾空格）
0x1120name歌曲名，不足补 0x00，末尾补 0x1A（DOS EOF）
0x251x1A固定 0x1A，用于校验
0x2620progName制作软件名。原版 FT2 写入 "FastTracker v2.00   "（空格填充）；本仓库写入 PROG_NAME_STR = "Fasttracker II clone"（ft2_module_saver.c:67-69）
0x3A2version格式版本，小端。本仓库仅接受 0x0102–0x0104
0x3C4headerSize头部扩展长度，以 0x3C 为起点计量。原版 FT2 恒为 276（= 20 + 256）
0x402numOrders歌曲长度（order 表有效条目数）
0x422songLoopStart循环回跳位置（order 索引）
0x442numChannels声道数（1–32 为正常范围）
0x462numPatterns模式数量
0x482numInstr乐器数量

尺寸自检：17+20+1+20 = 58（到 version 前）；加 2+4 = 64（到 headerSize 未）；再加 4×2 = 72；再加 4×2 = 80；再加 256 = 336。这正是 ft2_load_xm.c:71 中"文件总长恰为 336 即为空模块"判断的由来。

头部解析后，加载器执行 fseek(f, 60 + headerSize, SEEK_SET) 跳到第一段数据（ft2_load_xm.c:70）——注意是 60 + headerSize 而非 64，因为 headerSize 只覆盖 0x3C 之后的部分。

5. 模式数据（Pattern）

5.1 Pattern 头部

对应 xmPatHdr_t（ft2_replayer.h:112-122）：

偏移长度字段说明
0x004headerSize头部长度（v1.04 为 9，v1.02 为 8）
0x041type打包类型，恒为 0
0x052numRows行数（v1.02 为 1 字节，且存储值 = 实际行数 − 1）
0x072dataSize后续打包数据的字节数

v1.02 分支中行数的 "+1" 补偿见 ft2_load_xm.c:436。若 headerSize 大于标准值，加载器会前跳跳过扩展字节（ft2_load_xm.c:438-450），这保证了向前兼容。

5.2 打包（Packed）格式与解包算法

Pattern 数据是逐行、逐声道的 5 元组流：note、instr、vol、efx、efxData 各 1 字节。为压缩，XM 用一个"标志字节"控制后续字段是否存在：

读取 1 字节 b：
  if (b & 0x80) == 0:
      非压缩组 —— b 本身即 note，再直读 instr/vol/efx/efxData 共 4 字节
      → 共 5 字节
  else:
      压缩组 —— 各位独立表决该字段是否存在于流中：
        bit0 → note     存在则读 1 字节
        bit1 → instr    存在则读 1 字节
        bit2 → vol      存在则读 1 字节
        bit3 → efx      存在则读 1 字节
        bit4 → efxData  存在则读 1 字节
      缺省字段填充为 0

实现见 unpackPattern()（ft2_load_xm.c:500-568）。两个值得注意的工程细节：

  1. 溢出防护：解包函数带 bytesWritten >= unpackedBytes 检查，数据损坏时直接返回而非越界写（ft2_load_xm.c:517-518）。
  2. 超限声道的空转：当模块声道数超过 32 时，超出部分仍必须按压缩流语法正确跳过，否则后续字节全错位——代码为此写了一段只 src++ 不落盘的镜像逻辑（ft2_load_xm.c:542-562）。这是流式压缩格式的典型陷阱。

5.3 语义要点

  • note：0 表示空；1–96 对应显示音名 C-0 至 B-7（49 = C-4 = 中央 C）；97 = Key Off（松键）（ft2_replayer.h:55 NOTE_OFF 97）。
  • instr：乐器编号（1 基）。
  • vol：音量列，独立于效果列，编码见 5.4。
  • efx / efxData：效果号与参数。
  • 全空 pattern（tmpPatternEmpty()）会被释放并回退为默认 64 行（ft2_load_xm.c:478-487）。

5.4 音量列（Volume Column）编码

高 4 位为命令、低 4 位为参数。命令表由 v_* 函数与跳转表给出（ft2_replayer.c:1151-1165）：

0x1–0x5Set Volume直接设定音量（0–64）
0x6Volume Slide Down每 tick 减
0x7Volume Slide Up每 tick 加
0x8Fine Volume Slide Down仅 tick 0 生效

0xASet Vibrato Speed只改速度，不改深度

6. 乐器数据（Instrument）

这是 XM 相对 MOD 的核心结构性升级：MOD 只有 31 个扁平采样，XM 则引入"乐器"作为一层抽象——一个乐器最多容纳 16 个采样，并以 96 键映射表决定"哪个音符用哪个采样"。

两处与文档不符的实测细节（原版 FT2 的行为，本仓库如实复刻）：
  1. fadeout 的数值范围：XM 规范文档写作 0–65535，但原版 FT2 实际按 0–32768 处理。代码注释明确标注了这一点：ft2_replayer.c:389-390 中 ch->fadeoutVol = 32768，即淡出计数器的量程上限是 32768 而非 65536。
  2. volEnvPoints 的读取：无论 volEnvLength 是多少，加载器总是整块拷贝 12 个点（ft2_load_xm.c:236-237），因为磁盘上这 48 字节恒定存在。

6.2 采样头部（40 字节）

对应 xmSmpHdr_t（ft2_replayer.h:148-161）：

偏移长度字段说明
0x004length波形数据长度，单位为字节（16 位采样需 ×2 换算成采样点数）
0x044loopStart循环起点（字节）
0x084loopLength循环长度（字节）
0x0C1volume默认音量 0–64
0x0D1finetune有符号微调，原版范围 -128…127（存档时按 <<4 与 MOD 互转，见 FINETUNE_MOD2XM）
0x0E1flagsbit0–1 循环类型（0 无 / 1 前向 / 2 乒乓）；bit4 = 16 位；bit5 = 立体声（ModPlug 扩展）
0x0F1panning声像 0–255
0x101relativeNote相对音高，有符号。生效公式：relativeNote = (note>>4) - 48（ft2_replayer.c:163）

0x1222name采样名

长度换算要点：代码在内存中统一以"采样点数"为单位，因此加载 16 位采样时会先执行 length >>= 1、loopStart >>= 1、loopLength >>= 1（ft2_load_xm.c:349-354）。这也意味着 16 位采样的字节长度必须是偶数，否则奇数字节会错位。

7. 采样数据编码：Delta 差分

XM 的波形数据不是直接存放 PCM，而是差分（delta）编码：每个采样点存的是"与前一采样点的差值"，首点相对 0 计算。解码即前缀和：

// 8 位：逐字节累加（int8 自然溢出，等价于 int16 截断到 8 位）
news8 = data[i] + prev; data[i] = news8; prev = news8;

// 16 位：按 16 位字累加（小端 int16）
news16 = data16[i] + prev; data16[i] = news16; prev = news16;

实现见 delta2Samp()（ft2_replayer.c:2498-2577），保存时逆运算 samp2Delta()（ft2_replayer.c:2579）。

差分编码的实际收益是：波形中相邻点的差值通常远小于绝对值，配合压缩器可获得更好的压缩率。它是 Amiga MOD 起就存在的传统，XM 沿用。

7.1 立体声与混单

官方 XM 规范不支持立体声，但 ModPlug Tracker / OpenMPT 用 flags.bit5 扩展了它，数据布局为左声道整块在前、右声道整块在后（非交错）。本仓库支持读取但会在加载时下混为单声道（ft2_replayer.c:2503-2548 中 (L + R) >> 1），随后把长度与循环点减半并释放多余内存（ft2_load_xm.c:382-395）。

7.2 ADPCM 扩展（ModPlug）

若采样为 8 位单声道且保留字节为 0xAD，则该采样是 ModPlug 的 4-bit ADPCM 压缩格式（ft2_load_xm.c:299-300 置位 SAMPLE_ADPCM）。解码方式：先读 16 字节差分查表 deltaLUT[16]，再把每个字节的高/低 4 位分别作为查表索引累加，每次输出 2 个采样点（ft2_load_xm.c:570-589）。

这是 ModPlug 的私有扩展，不是 XM 规范的一部分，但已成为事实兼容性要求。

8. 频率表：XM 最重要的设计决策

头部 flags 的 bit 0 决定音高换算用哪张表，这是 XM 与 MOD 分道扬镳的关键点，也是"线性频率表（Linear Frequency Table）"这一术语的来源。

8.1 两种模式

flags.bit0 = 0 → Amigaflags.bit0 = 1 → Linear
音高曲线沿用 MOD 的 Amiga period 表按对数（等音程）插值
移调/滑音听感非线性线性，音程听感均匀
与 MOD 兼容性高低（同一效果参数听感不同）

Amiga 模式下 period 与实际频率成反比；线性模式下 period 是半音等差的，因此"每 tick 固定步长的滑音"在任何音区都产生相同的音分变化量，这让滑音、颤音的手感更可预测——这正是 FastTracker II 推广线性表的动机。

本仓库用两张 1936 项 uint16 查找表实现，且声明为"与原版 FT2 逐比特一致"（ft2_tables.c:61 linearPeriodLUT，ft2_tables.h:16-17）：

extern const uint16_t linearPeriodLUT[1936];  // 线性频率表
extern const uint16_t amigaPeriodLUT[1936];   // Amiga (MOD) 频率表

索引计算 = note * 16 + ((finetune >> 3) + 16)（ft2_replayer.c:292），即"每半音 16 个插值档位 × 微调细分"。加载时：

tmpLinearPeriodsFlag = !!(header.flags & 1);   // ft2_load_xm.c:85

运行时通过函数指针切换整表：setLinearPeriods() 令 note2PeriodLUT = linearPeriodLUT 或 amigaPeriodLUT（ft2_replayer.c:315-324）。保存时则回写 h.flags = audio.linearPeriodsFlag（ft2_module_saver.c:97）。

8.2 实践含义

打开或导入 XM 时必须先读 flags 再初始化播放器，否则所有音高、滑音、颤音都会整体偏移。这也是跨 tracker 迁移模块时"听起来不对"的头号原因。

9. 本仓库实现中的兼容性处理与限制

ft2-clone 以"加载更多、丢弃更多"为策略，对超出原版 FT2 能力的文件做了如下处理。这些常量定义在 src/ft2_replayer.h:51-65：

常量值含义
MAX_CHANNELS32最大声道数
MAX_PATTERNS256最大 pattern 数
MAX_PATT_LEN256单 pattern 最大行数
MAX_ORDERS256最大 order 数
MAX_INST128最大乐器数
MAX_SMP_PER_INST16每乐器最大采样数
INSTR_HEADER_SIZE263乐器头部标准长度
MAX_SAMPLE_LEN0x3FFFFFFF单采样最大长度

具体降级行为：

  1. 声道数 > 32：保留前 32 声道，其余丢弃并弹出警告；pattern 解包阶段仍需按压缩语法空转跳过超限声道数据（ft2_load_xm.c:173-177、500-567）。
  2. 乐器数 > 128：临时加载后在收尾阶段释放，仅前 128 个保留（ft2_load_xm.c:63-64, 142-153, 179-180）。
  3. 乐器采样数 > 16（ModPlug 最多 32）：只保留前 16 个，额外采样头部的长度被暂存到 extraSampleLengths[16] 以便正确跳过其数据，最终丢弃（ft2_load_xm.c:20, 270-279, 399-408）。
  4. order 数：文件允许 256，但 FT2 仅支持 255，超出部分截断（ft2_load_xm.c:102-104）。
  5. order 表被 0xFF 填充：从尾部向前扫描并收缩有效长度（ft2_load_xm.c:92-100）。
  6. pattern 行数 > 256：截断到 256 并提示（ft2_load_xm.c:457-461, 490-491）。
  7. 乐器头部长度异常：为 0 或超过 263 时按 263 处理；大于 263 时跳过扩展字节（ft2_load_xm.c:199-213）。
  8. 版本校验：仅接受 0x0102–0x0104，其余报错退出（ft2_load_xm.c:44-49）。
  9. 空文件判定：读取头部后若文件恰好结束于偏移 336，判定为"空模块"报错（ft2_load_xm.c:71-75）。

任何一处跳字节计算错误都会导致后续整条流错位，因此上述 3、4、6 项均采用"先记录长度、再在正确阶段精确 fseek"的两段式策略。

10. 保存侧（导出 XM）

saveXM()（ft2_module_saver.c:31）的输出恒为 v1.04：

  • h.version = 0x0104，h.headerSize = 20 + 256 = 276（ft2_module_saver.c:71-72）
  • 程序名以空格填充至 20 字节（原版 FT2 同样如此，ft2_module_saver.c:67-69）
  • 头部的 instrSize 恒写 263，且整个乐器头部先 memset 清零以清空保留字段（ft2_module_saver.c:150, 200）
  • 采样写出前把内部 PCM 转为差分：samp2Delta() → 写盘 → delta2Samp() 还原内存态（ft2_module_saver.c:257-263），保证内存数据不被破坏

体积估算逻辑可参见 src/ft2_trim.c：有采样的乐器按 INSTR_HEADER_SIZE + n × sizeof(xmSmpHdr_t) 计，无采样的"空乐器"占 22 + 11 字节（ft2_trim.c:131-133）。

结论：XM 是"曲谱 + 多采样乐器 + 包络自动化 + 双频率表"的二进制容器格式，其解析难点集中在三点——三段顺序随版本变化、pattern 的位标志流式压缩、flags.bit0 决定的频率表模式。任何 XM 实现只要把这三处处理正确，其余部分都是常规的定长/变长结构搬运。
